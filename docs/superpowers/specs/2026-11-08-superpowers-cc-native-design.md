# superpowers-cc-native: дизайн v0

- Дата: 2026-11-08.
- Статус: все пять разделов одобрены владельцем 2026-11-08. Спека ждёт его ревью.
- Следующий шаг: план в `docs/superpowers/plans/`.

## 1. Зачем это

`superpowers-cc-native` - свой fork плагина
[obra/superpowers](https://github.com/obra/superpowers) для Claude Code
(дальше CC). Мы только добавляем возможности CC. Поддержку других сред не
вырезаем: их пользователям остаётся оригинал.

**Главный критерий всех решений - лёгкая поддержка:**

- новый релиз оригинала забирается быстро и почти без ручной работы;
- наши доработки растут, а цена обновления до оригинала вместе с ними не растёт.

Опыт существующего fork `pcvelz/superpowers` показывает, что ломает этот
критерий:

- скиллы переписаны прямо в файлах оригинала;
- файлы оригинала удалены;
- переименование делается руками;
- история оригинала вливается целиком, а оригинал её переписывал;
- номера версий идут в одном ряду с номерами оригинала.

В итоге каждое обновление тяжёлое, и fork отстаёт на несколько релизов.

**v0** - чистый оригинал 7.0.2 под нашим именем, без доработок. Его задача -
механизм: импорт релиза, проверки, выпуск, установка. Доработки пойдут после
v0 и только по потребности, когда станет видно, как работает оригинал.

## 2. Цели, не цели, анти-цели

**Цели v0**

1. Релиз оригинала забирается одной командой `node tools/sync.mjs <тег>`.
   Ручная работа нужна только там, где мы и оригинал правили одно место.
2. Наши отличия всегда видны одной командой: `git diff upstream main -- plugin/`.
3. Рост (свои скиллы, справки, хуки) не добавляет конфликтов при импорте.
4. Пользователь ставит плагин одной командой и получает обновление, когда
   меняется номер версии.
5. Выпуск защищён проверками: изменённый плагин со старым номером выпустить
   нельзя.

**Не цели v0**

- поддержка других сред, кроме CC;
- любые доработки скиллов, перенос возможностей pcvelz;
- CI (в том числе на двух ОС), шаблоны issue, GitHub Releases;
- автообновление;
- проверка своих добавок на Windows.

**Анти-цели** (провал, даже если всё работает)

- ручные коммиты в ветку `upstream`;
- переписывание скиллов оригинала на месте и удаление его файлов;
- переименование руками;
- номера версий, которые можно спутать с номерами оригинала; `-dev` в `main`;
- зависимости у `tools/`;
- личные и инфраструктурные данные в репозитории.

## 3. Ограничения

- Репозиторий публичный с первого дня. В нём нет личных и инфраструктурных
  данных: ни хостов, ни путей машины, ни профилей, ни проектов владельца.
- Коммиты и push - только по явному слову владельца.
- `tools/` - Node.js 24 или новее, без зависимостей: только встроенные модули
  и `node:test`.
- Каждый `plugin/skills/*/SKILL.md` меньше 20 000 байт. После сжатия контекста
  CC возвращает каждый вызванный скилл только первыми 5 000 токенами, на все
  скиллы вместе - 25 000 токенов. Оригинал переводит это в лимит 20 000 байт,
  и его тест `skill-size` падает на этом размере.
- Имя плагина задаёт пространство имён скиллов. Переименованный плагин для CC
  - другой плагин, поэтому ссылки `superpowers:<скилл>` в тексте оригинала
  нужно менять.
- Репозиторий на GitHub не fork оригинала: форки не попадают в поиск кода, а
  PR из форка по умолчанию открывается в оригинал.

## 4. Подходы

Рассмотрены четыре способа держать свои правки поверх оригинала. Три из них
проверены пробным прогоном 2026-11-07. Поверх v6.3.0 делались три пробные
правки в одну строку, затем импортировались пять следующих настоящих релизов:

- указатель в конце `SKILL.md` у subagent-driven-development;
- такой же указатель у executing-plans;
- правка строки «writing-plans skill» в brainstorming.

| Релиз | Две ветки | Патчи поверх снимка (A) | Обычный fork (B) |
|---|---|---|---|
| 6.4.1 | executing-plans | executing-plans | 5 файлов, 6 мест: манифесты, CLAUDE.md, executing-plans, writing-plans |
| 6.4.2 | чисто | чисто | 2 файла: манифесты |
| 7.0.0 | brainstorming | brainstorming | 3 файла: манифесты, brainstorming |
| 7.0.1 | executing-plans, SDD | SDD, executing-plans | 22 файла, 8 мест, в основном переименование |
| 7.0.2 | чисто | чисто | 3 файла: манифесты, session-start |

- **Две ветки (vendor branch) - выбран владельцем 2026-11-08.**
  - Ветка `upstream` получает только импорты релизов, уже переименованные
    скриптом.
  - `main` - это `git merge upstream` плюс наши коммиты.
  - Основа слияния - прошлый импорт, и обе стороны уже переименованы. Поэтому
    конфликт бывает только там, где мы и оригинал правили одно место.
  - Так же устроены vendor branch в CVS и Subversion и `gbp import-orig
    --merge` в Debian (DEP-14).
- **A. Патчи поверх снимка.** Конфликты те же, потому что оба способа сводятся
  к трёхстороннему слиянию. А своего кода для применения патчей больше.
- **B. Обычный fork.** Конфликты на каждом релизе: переименование и манифесты
  каждый раз расходятся с оригиналом.
- **Плагин-надстройка через `dependencies`.** Не годится: `skillOverrides` не
  действует на скиллы плагинов. Скрыть или заменить скилл оригинала нельзя, и
  в сессии будут два набора.

## 5. Раскладка репозитория

Репозиторий `Stashub/superpowers-cc-native` на GitHub. `Stashub` - аккаунт
типа User. Репозиторий публичный, не fork. На 2026-11-08 он ещё не создан.

### 5.1. Ветка `upstream`

- содержит только `plugin/` - релиз оригинала после импорта;
- на каждый релиз один коммит и annotated тег `upstream/v<версия>`;
- писать в неё может только `tools/sync.mjs`. Рабочая копия на неё не
  переключается.

### 5.2. Ветка `main` (её ставят пользователи)

| Путь | Что это |
|---|---|
| `plugin/` | сам плагин: всё из `upstream` плюс наши правки. Из оригинала ничего не удаляем |
| `.claude-plugin/marketplace.json` | marketplace с одним плагином. Единственное место, где записан наш номер версии. В `plugin/package.json` остаётся номер оригинала: CC его не читает, его показывает только страница компаньона (раздел 11) |
| `README.md` | что это и для кого (пользователям других сред - ссылка на оригинал), установка, отличия от оригинала, куда писать об ошибках, коротко о том, как подтягивать оригинал |
| `CHANGELOG.md` | наши выпуски `-cc.N` (раздел 8) |
| `LICENSE` | MIT с двумя строками копирайта: `Copyright (c) 2025 Jesse Vincent` и `Copyright (c) 2026 Stashub`. В `plugin/LICENSE` остаётся лицензия оригинала |
| `CLAUDE.md` | правила для агента, который сопровождает репозиторий (5.4) |
| `tools/` | `sync.mjs` (импорт и слияние), `check.mjs` (проверки) и их тесты |
| `tools/hooks/pre-push` | git-хук: не пропускает push `main` без выпуска и push `upstream` с нарушенной печатью (раздел 8) |
| `.gitattributes` | `eol=lf` только для наших путей (`/tools/`, `/docs/`, корневые файлы). Общих шаблонов вроде `* text=auto` или `*.md` нет: они задели бы `plugin/`, и файл оригинала мог бы показаться изменённым после checkout. Тогда рабочая копия «грязная», и sync останавливается |
| `.gitignore` | в том числе строка `.superpowers/` |
| `docs/superpowers/specs/`, `docs/superpowers/plans/` | эта спека и планы |

Про `.gitignore`: журнал SDD (`.superpowers/sdd/`) оригинал прячет сам, своим
`.gitignore`. Файлы визуального компаньона (`.superpowers/brainstorm/`, включая
токен сервера `.last-token`) он не прячет.

`plugin/.github/` и `plugin/.gitattributes` оригинала остаются на месте.
GitHub читает только корневой `.github/`, а `plugin/.gitattributes` действует
только внутри `plugin/`. CI и шаблоны issue - после v0.

`.claude-plugin/marketplace.json` для первого выпуска:

```json
{
  "name": "superpowers-cc-native",
  "owner": { "name": "Stashub", "url": "https://github.com/Stashub" },
  "description": "Claude Code native fork of obra/superpowers",
  "plugins": [
    { "name": "superpowers-cc-native", "source": "./plugin", "version": "7.0.2-cc.1" }
  ]
}
```

Имя marketplace совпадает с именем плагина.

### 5.3. Язык и почта

- README, CHANGELOG, CLAUDE.md и сообщения коммитов - на английском. Сам
  плагин на английском, и читать его будут не только мы.
- Почта в коммитах - noreply-адрес GitHub
  `64739874+Stashub@users.noreply.github.com`. Он задаётся `git config
  user.email` только в этом репозитории, тот же адрес у коммитов `upstream`.
  Почта из глобального git config не должна попасть в историю.
- Имя в коммитах и тегах (автор, коммиттер, tagger) - `Stashub`, тоже через
  `git config user.name` только в этом репозитории. Глобальное имя на машине
  другое, и в публичную историю оно попасть не должно: после push его
  убирает только переписывание истории. (Решение агента при ревью спеки.)

### 5.4. `CLAUDE.md` репозитория

Правила для агента:

- в `upstream` руками не писать и на эту ветку не переключаться;
- своё держать в своих файлах (раздел 10);
- `SKILL.md` меньше 20 000 байт;
- изменения `plugin/` попадают в `main` только вместе с выпуском, и каждый
  выпуск получает новый номер;
- шаги импорта и выпуска (разделы 6 и 8);
- каждая наша правка добавляет строку в раздел `Unreleased` в CHANGELOG, в том
  же коммите;
- личных и инфраструктурных данных в репозитории нет;
- коммит и push - только по слову владельца.

## 6. Импорт и слияние: `node tools/sync.mjs <тег>`

### 6.1. Как забираем оригинал

```
git fetch --no-tags https://github.com/obra/superpowers.git +refs/tags/v7.0.3:refs/obra/tags/v7.0.3
```

- `+` нужен на случай, если оригинал перенёс тег на коммит не из прежней
  истории: без него повторный fetch откажет.
- Ссылки `refs/obra/*` не пушатся и не смешиваются с нашими тегами.
- Remote с именем `upstream` не заводим: это имя занято веткой.
- Параметр `--from <адрес или путь>` подменяет адрес оригинала. Он нужен
  тестам: оригинал берётся из локального клона без сети.

### 6.2. Сборка коммита импорта

Коммит собирается без рабочей копии, через временный индекс:

1. Скрипт обходит файлы тега: `git ls-tree -r -z`.
2. `.claude-plugin/marketplace.json` пропускается, если он есть.
3. `.claude-plugin/plugin.json` преобразуется (6.4).
4. В каждом текстовом файле (blob без NUL-байтов, не symlink) делается замена
   (6.3). Результат пишется через `git hash-object -w --stdin --no-filters`.
   Остальные blob, включая symlink (в v6.3.0 он есть), переносятся как есть.
   Режим файла сохраняется. Замена побайтовая: blob читается как latin1 и так
   же записывается, а всё вне совпадений остаётся байт в байт. Иначе файл не
   в UTF-8 испортился бы при перекодировке.
5. Записи с префиксом `plugin/` кладутся во временный индекс (`GIT_INDEX_FILE`,
   `git update-index -z --index-info`), затем `git write-tree`.
6. `git commit-tree <дерево> -p <прошлый импорт>`. У первого импорта родителя
   нет. Затем `git update-ref refs/heads/upstream`.
7. Ставится annotated тег `upstream/v<версия>`.

Почему так, а не распаковкой архива в рабочую копию:

- рабочая копия всё время на `main`, и случайно закоммитить в `upstream`
  нельзя;
- дерево не зависит от локальных настроек git (`core.autocrlf`, фильтры).

2026-11-08 на v7.0.2 этот способ и `git archive | tar -x` дали одно и то же
дерево. Один тег при одних правилах импорта всегда даёт одно дерево; это
свойство проверяют модульные тесты.

Сообщение коммита:

```
upstream v7.0.3 (<короткий sha>)

Upstream-Tag: v7.0.3
Upstream-Commit: <полный sha>
Sync-Tree: <полный хэш дерева этого коммита>
```

**Печать `Sync-Tree`** (выбор владельца 2026-11-08 при ревью спеки). sync
сначала строит дерево, затем пишет его хэш в сообщение и только потом
создаёт коммит. Поэтому печать всегда равна дереву коммита, который сделал
sync. По ней проверка «`upstream` правили руками» (6.8) обходится без
пересборки:

- ручной коммит в `upstream` приходит без печати;
- исправленный коммит (`--amend` с другим содержимым) не совпадает со своей
  печатью.

Теги оригинала для проверки не нужны, поэтому перенос тегов и переписывание
истории у оригинала нас не задевают. Правила импорта (6.3, 6.4) можно
менять: следующий импорт просто получит новое дерево со своей печатью.

Отвергнуто: пересборка прошлого импорта из тега оригинала. Если оригинал
перенесёт тег (историю он уже переписывал в сентябре 2026), такая проверка
останавливает все следующие импорты, а выход из неё - только ручная правка
`upstream`.

### 6.3. Переименование

- **Где:** все текстовые файлы `plugin/`. Это включает исторические тексты
  (`RELEASE-NOTES.md`, `docs/plans/`) и файлы других сред. Другие среды при
  этом ломаются, но мы их не поддерживаем. Зато проверка простая: во всей
  `plugin/` ноль старых ссылок.
- **Что:** regex `(?<![\w-])superpowers:(?=[a-z])` заменяется на
  `superpowers-cc-native:`. Граница слева защищает от будущих слов вида
  `foo-superpowers:x`. Повторное применение ничего не меняет.
- **Объём в 7.0.2:** 42 файла, 94 ссылки. По папкам: skills 21 файл / 48
  ссылок, docs 10/19, `RELEASE-NOTES.md` 1/12, tests 4/6, ещё 6 файлов по 1-3
  ссылки. Все совпадения - ссылки на компоненты плагина: скиллы (в том числе
  удалённый `testing-anti-patterns` и шаблон `skill-name` в writing-skills),
  старая команда `/superpowers:brainstorm` и бывший агент `code-reviewer`.
  Ложных нет.
- **Не трогаем** другие упоминания имени: `"name": "superpowers"` в манифестах
  других сред и в `package.json`, команды установки в README оригинала.

### 6.5. Слияние

1. От `main` создаётся ветка `sync/v7.0.3`. В неё делается `git merge --no-ff
   upstream` с сообщением `Merge upstream v7.0.3`.
2. При первом импорте у `main` и `upstream` нет общей основы. Скрипт сам
   добавляет `--allow-unrelated-histories`. Конфликтов нет: в `upstream` есть
   только `plugin/`, а в `main` к этому моменту `plugin/` ещё нет.
3. Отчёт:
   - слилось чисто или в каких файлах конфликты;
   - счётчик наших строк в файлах оригинала: `git diff --numstat upstream HEAD
     -- plugin/`;
   - затем вывод `check.mjs`.
4. При конфликте скрипт останавливается, ветка остаётся в состоянии слияния.
   Конфликт разрешают, делают коммит и запускают `check.mjs`.
5. Дальше в этой же ветке делается выпуск (раздел 8). После слова владельца
   `main` переводится на ветку через `--ff-only`, ветка `sync/*` удаляется.

### 6.6. Повторный запуск

Тег уже импортирован (он равен `Upstream-Tag` вершины `upstream`) - новый
коммит в `upstream` не создаётся.

- `upstream` уже влит в текущую ветку: скрипт сообщает «нечего делать» и
  выходит с кодом 0, ничего не меняя.
- Не влит: выполняется слияние (6.5).

### 6.7. Свежий клон и вторая машина

Ветка `upstream` живёт и локально, и на GitHub. Если перепутать их, sync
построит импорт не на той основе. Правила:

- Если есть remote `origin`, sync сначала делает `git fetch origin`.
- Локальной `upstream` нет, а `origin/upstream` есть (свежий клон): sync
  создаёт локальную ветку из `origin/upstream` и работает от неё.
- Локальная `upstream` отстаёт от `origin/upstream` или разошлась с ней: стоп.
  Иначе новый импорт лёг бы на устаревшую основу, и push `upstream` не прошёл
  бы.
- Первый импорт (без родителя) - только если `upstream` нет ни локально, ни
  в `origin`.
- `check.mjs` при отсутствии локальной `upstream` берёт `origin/upstream`.
- В свежем клоне первым делом задаётся локальный config: имя, почта (5.3) и
  `core.hooksPath tools/hooks` (раздел 8). Без имени и почты sync
  останавливается (6.8), `check.mjs --release` тоже. Шаги записаны в
  CLAUDE.md.

### 6.8. Когда скрипт останавливается

| Случай | Как определяется |
|---|---|
| рабочая копия грязная | `git status --porcelain` не пуст |
| у оригинала нет такого тега | fetch не нашёл ссылку |
| тег не из оригинала | `name` в `.claude-plugin/plugin.json` тега не `superpowers` |
| тег не новее прошлого импорта | сравнение по semver с `Upstream-Tag` последнего импорта. Тот же тег - случай 6.6 |
| `upstream` правили руками | у какого-то коммита `upstream` (по `--first-parent`) нет трейлеров `Upstream-Tag` и `Sync-Tree`, или его дерево не равно `Sync-Tree` |
| локальная `upstream` отстаёт от `origin/upstream` или разошлась с ней | 6.7 |
| в config репозитория не те имя и почта | `git config user.name` не `Stashub` или `user.email` не noreply-адрес из 5.3. Защищает свежий клон: без локального config git возьмёт глобальные имя и почту, и они попадут в публичную историю |

### 6.9. Тесты sync

- **Модульные** (`node:test`, временные репозитории): замена, `plugin.json`,
  детерминизм, каждая остановка из 6.8, правила свежего клона из 6.7,

  - в `main` три пробные правки из раздела 4. Указатели ведут на свои файлы

## 7. Проверки: `node tools/check.mjs`

Два уровня. Номер версии меняется только при выпуске, а `plugin/` между
выпусками меняется постоянно. Если проверять номер на каждом коммите,
проверка будет падать зря.

### 7.1. Обычная проверка

Запускается после `sync.mjs` и перед любым коммитом. Занимает несколько секунд.

1. В `plugin/` нет совпадений с regex из 6.3.
2. `plugin/.claude-plugin/plugin.json`: `name` равен `superpowers-cc-native`,
   `version` нет.
3. `plugin/.claude-plugin/marketplace.json` отсутствует.
4. Корневой `.claude-plugin/marketplace.json`:
   - есть `name`, `owner.name`, `description`;
   - ровно один плагин, `name` равен `superpowers-cc-native`, `source` равен
     `./plugin`;
   - версия соответствует `^\d+\.\d+\.\d+-cc\.[1-9]\d*$`.
5. `claude plugin validate . --json` и `claude plugin validate ./plugin --json`
   (7.3).
6. Тесты оригинала без модели (7.4).
7. Для сведения: счётчик наших строк в файлах оригинала, `git diff --numstat
   upstream HEAD -- plugin/`.

### 7.2. `check.mjs --release` и `--push`

Запускается перед коммитом выпуска. Включает всё из 7.1, проверку имени и
почты в config (как в 6.8), плюс номер:

- **Основа** - `Upstream-Tag` коммита `git merge-base HEAD upstream`, без `v`.
- **Прошлый выпуск** - самый старший по semver тег `v*-cc.*`, достижимый из
  `HEAD`.
- **Ожидаемый номер:**
  - выпусков ещё нет, или основа прошлого выпуска другая - `<основа>-cc.1`;
  - иначе `<основа>-cc.<N+1>`.

  Скрипт печатает ожидаемый номер. Принимается только он, без пропусков.

Проверка проходит в одном из двух случаев:

- **Выпускать нечего:** дерево `plugin/` в `HEAD` равно дереву `plugin/` у
  прошлого выпуска, а номер в marketplace равен номеру прошлого выпуска. Сюда
  попадает и состояние сразу после тега, и коммиты, которые меняют только
  файлы вне `plugin/`. До первого импорта, когда нет ни `plugin/`, ни
  выпусков, выпускать тоже нечего.
- **Готовится выпуск:** `plugin/` изменился, номер равен ожидаемому, в CHANGELOG
  есть заголовок `## <номер> - YYYY-MM-DD`, тега `v<номер>` ещё нет.

Всё остальное - ошибка. Например:

- `plugin/` изменился, а номер прежний;
- номер сменили, а `plugin/` не менялся;
- тег `v<номер>` стоит на другом коммите.

**Режим `check.mjs --push <коммит>`.**

Запускает его хук `pre-push` (раздел 8), когда отправляется `main`. Работает
по объектам git, без рабочей копии: validate и тесты уже прошли при
выпуске. Проверяет номер по правилам 7.2 для указанного коммита и принимает
только случай «выпускать нечего». В `main` на GitHub уходит только
выпущенное и помеченное тегом. Если выпуск подготовлен, но тега ещё нет, push
не проходит.

### 7.3. `claude plugin validate`

- Проверяем оба пути. Проверка `.` проходит, даже если папки `plugin/` нет
  вовсе.
- `--strict` не используем. Он падает всегда: предупреждает «в plugin.json нет
  version» (`No version specified`), даже когда номер стоит в записи
  marketplace. А убрать `version` - наше решение.
- Читаем ответ `--json`. Провал - любая ошибка и любое предупреждение в
  `manifest` и `contents`, кроме этого одного. Строгость нужна: битый
  frontmatter скилла validate считает только предупреждением.
- Не учитываем:
  - `advice`. Сейчас там совет про строку установки в `plugin/README.md`, а
    это файл оригинала;
  - `directory`, проверки каталога плагинов Anthropic. Сейчас там
    `ICON_MISSING` (`blocking: false`). Сам validate пишет, что эти проверки
    на результат не влияют.
- Нет `claude` в PATH: в обычной проверке пункт пропускается с заметным
  предупреждением, в `--release` это ошибка.

Формат ответа `--json` (CC 2.1.319): `success`, `manifest.errors[]`,
`manifest.warnings[]` (`path`, `message`, `code`), `contents[]` с теми же
`errors` и `warnings` по файлам, `advice[]`, `directory.findings[]`
(`code`, `severity`, `blocking`).

## 8. Выпуск

**Главное правило: изменения `plugin/` попадают в `main` только вместе с
выпуском.** CC забирает обновление, только когда меняется номер версии.
Допустим, в `main` на GitHub окажется новый `plugin/` со старым номером. Тогда
те, кто уже поставил плагин, обновления не получат, а новые пользователи
получат другое содержимое под тем же номером.

- Работа идёт в отдельных ветках: `sync/*`, ветки планов.
- Коммит выпуска делается в той же ветке до перевода `main`.
- Правки вне `plugin/` (README, `tools/`, CLAUDE.md) выпуска не требуют.

**Номер** - `<версия оригинала>-cc.N`: 7.0.2-cc.1, 7.0.2-cc.2, 7.0.3-cc.1.
Его вычисляет `check.mjs --release` (7.2).

- Формат `+cc.N` не берём: semver не учитывает часть после `+` при сравнении.
- `-dev` в `main` не бывает.

**Теги:** наши - `v7.0.2-cc.1`, импорты - `upstream/v7.0.2`. Все annotated
(`git tag -a`): push с `--follow-tags` отправляет только такие. Теги оригинала
в `refs/tags` не тянем.

**CHANGELOG.md** (на английском):

- Вверху раздел `## Unreleased`. Каждая наша правка добавляет туда строку в
  том же коммите.
- При выпуске раздел получает номер и дату, а над ним ставится новый пустой
  `Unreleased`.
- Изменения оригинала описаны в `plugin/RELEASE-NOTES.md`, у нас на них
  ссылка.

```markdown
# Changelog

## Unreleased

## 7.0.3-cc.1 - YYYY-MM-DD
Based on obra/superpowers v7.0.3 (their changes: plugin/RELEASE-NOTES.md).
- No changes of our own.

## 7.0.2-cc.1 - YYYY-MM-DD
Based on obra/superpowers v7.0.2.
- First release: the original renamed to superpowers-cc-native.
```

**Шаги.** Отдельного скрипта нет: шагов мало, они записаны в CLAUDE.md
репозитория.

1. В ветке: номер в `.claude-plugin/marketplace.json`, `Unreleased`
   переименовывается в номер с датой.
2. `node tools/check.mjs --release`.
3. Коммит `Release v<номер>`. `main` переводится на ветку через `--ff-only`,
   ставится тег `v<номер>`. Если `main` за это время ушёл вперёд (например,
   влит импорт), `--ff-only` откажет. Тогда сначала `main` вливается в ветку,
   и шаги 1-2 повторяются: номер мог измениться.
4. `git push --follow-tags origin main upstream`. Ветка `upstream` тоже уходит
   на GitHub, чтобы `git diff upstream main` работал у всех.

На шаги 1-3 нужно одно слово владельца, на шаг 4 - отдельное.

**Блокировка, а не только процедура** (решение агента при ревью спеки).
Чтобы цель 5 держалась не только на том, что агент выполнит шаги:

- `tools/hooks/pre-push` читает со stdin, какие ссылки и коммиты уходят.
  Проверяется отправляемый коммит, а не `HEAD`: `main` можно пушить, стоя на
  другой ветке.
  - Уходит `refs/heads/main`: `node tools/check.mjs --push <коммит>` (7.2, режим `--push`).
  - Уходит `refs/heads/upstream`: проверка печати `Sync-Tree` у всех его
    коммитов (как в 6.8). Исправить испорченный `upstream` после публикации
    можно только переписыванием публичной истории.
  - Не прошло - push отменяется.
- Хук включается на шаге «репозиторий» командой `git config core.hooksPath
  tools/hooks`, только в этом клоне.
- Push других веток хук не проверяет. Отдельного хука на коммит нет: обычную
  проверку запускают руками, по CLAUDE.md.

Первый выпуск - `7.0.2-cc.1`. GitHub Releases - после v0.

## 9. Установка и переход (для README)

- **Установка одной командой** (CC 2.1.275 и новее):

  ```
  claude plugin install superpowers-cc-native --marketplace Stashub/superpowers-cc-native
  ```

  Команда сама добавляет marketplace в настройки пользователя, scope по
  умолчанию `user`.
- **Для старых версий CC:**

  ```
  claude plugin marketplace add Stashub/superpowers-cc-native
  claude plugin install superpowers-cc-native@superpowers-cc-native --scope user
  ```

- **Переход с оригинала.** Сначала выключить оригинал, потом поставить наш.
  Так ни одна новая сессия не получит два набора скиллов и два SessionStart.
  Оригинал ставят из двух marketplace, выключать нужно тот, что стоит
  (видно в `claude plugin list`):

  ```
  claude plugin disable superpowers@superpowers-marketplace --scope user
  claude plugin disable superpowers@claude-plugins-official --scope user
  ```

  Не удалять оригинал, пока на нём работают сессии. В конце проверить `claude
  plugin list`. В командах ниже `superpowers@superpowers-marketplace` для
  пользователей официального marketplace заменяется на
  `superpowers@claude-plugins-official`.
- **Имена скиллов меняются:** `/superpowers:brainstorming` становится
  `/superpowers-cc-native:brainstorming`. Ссылки в своих CLAUDE.md и заметках
  нужно поправить.
- **Работающие сессии** остаются на старом плагине до `/reload-plugins`, `/cd`,
  перезапуска или `--resume`. `--resume` поднимает плагин, установленный
  сейчас.
- **План, начатый на оригинале, доводится на нём:**

  ```
  claude --resume <id> --settings '{"enabledPlugins":{"superpowers@superpowers-marketplace":true,"superpowers-cc-native@superpowers-cc-native":false}}'
  ```

- **Откат:** выключить наш плагин (`claude plugin disable
  superpowers-cc-native@superpowers-cc-native --scope user`) и включить оригинал
  (`claude plugin enable superpowers@superpowers-marketplace --scope user`).
- **Обновления - вручную.** Для сторонних marketplace автообновление по
  умолчанию выключено, и мы его не включаем:

  ```
  claude plugin marketplace update superpowers-cc-native
  claude plugin update superpowers-cc-native@superpowers-cc-native
  ```

  Новая версия загружается в следующей сессии или после `/reload-plugins`.
  Работающая сессия остаётся на старой версии, но папку старой версии CC
  удаляет из кэша через 14 дней после обновления. Если сессия должна идти
  дольше, обновление лучше отложить до её конца.

## 10. Правила роста

От этих правил зависит, останется ли поддержка лёгкой, когда доработок станет
много.

1. **Своё - в своих файлах:**
   - свои скиллы - `plugin/skills/cc-<имя>/`;
   - свои справки к скиллам оригинала - `plugin/skills/<скилл>/references/cc-<тема>.md`;
   - свои хуки - отдельный файл `plugin/hooks/cc-native.json`. Он подключается
     полем `hooks` в `plugin.json`, и CC грузит его вместе с
     `hooks/hooks.json`.
2. **Префикс `cc-`** у своих файлов внутри папок оригинала. Если оригинал
   завтра добавит файл с тем же именем, будет конфликт add/add.
3. **В файлах оригинала - минимум**, лучше одна строка-указатель на свой файл.
   Указатель ставится в том шаге, где он нужен, а не в конце файла. После
   сжатия контекста CC возвращает только первые 5 000 токенов скилла, и конец
   большого `SKILL.md` может пропасть.
4. **Если скилл оригинала нужно переделать целиком,** рядом делается свой
   скилл с другим именем, а скилл оригинала не трогаем.
5. **Каждая доработка необязательна.** Если нужной возможности CC нет, плагин
   работает как оригинал. Источник правды - план и журнал, инструменты задач
   только дополняют их.
6. **`SKILL.md` меньше 20 000 байт**, вместе с нашими строками. Запас у
   `subagent-driven-development/SKILL.md` после переименования - 229 байт
   (файл 19 770 байт, предел 19 999). У `executing-plans` - около 1 500 байт
   (18 494). Всё, что длиннее строки-указателя, идёт в `references/`.

   Редкий случай: файл оригинала перерос лимит только из-за переименования
   (каждая ссылка длиннее на 10 байт). Это ошибка проверки, как и у
   оригинала. Выход - короткая правка этого файла в `main`, без переписывания
   скилла. Она записывается в CHANGELOG, а оригиналу сообщаем, что запаса у
   скилла почти нет. (Решение агента при ревью спеки.)
7. **Каждый релиз оригинала забираем сразу:** маленькие шаги дают маленькие
   конфликты.
8. **Счётчик наших строк** в файлах оригинала (отчёт sync и check) показывает,
   растёт ли расхождение. Растёт - значит, своё пора выносить в свои файлы.

  - PR только в `dev` и по правилам их AGENTS.md и шаблона PR.

  Правила оригинала для PR:
  - одна проблема на PR, и она из реальной сессии;
  - указаны модель, среда и все плагины;
  - сводку до 200 слов пишет человек;
  - правки текста скиллов - только с evals до и после;
  - PR с особенностями fork, ребрендингом или синхронизацией fork закрывают.

## 12. Состав v0

1. Репозиторий: `git init`, корневые файлы (раздел 5), в локальном config
   noreply-почта, имя `Stashub` и `core.hooksPath tools/hooks`.
2. `tools/sync.mjs` с тестами, первый импорт v7.0.2.
3. `tools/check.mjs` с тестами.
4. Проба `--plugin-dir` (7.5).
5. Выпуск `7.0.2-cc.1`.
6. Создание репозитория на GitHub (`gh repo create`) и push. Только по слову
   владельца.
7. Установка и переход (раздел 9). Делает владелец или агент по его слову.

Разбиение на задачи и их порядок - в плане. Отложено: CI на двух ОС,
автообновление, проверка Windows для своих добавок, перенос возможностей
pcvelz.

## 13. Что решает строитель

- Устройство кода `sync.mjs` и `check.mjs`: модули, имена функций, общий код
  (замена и regex должны быть в одном месте для обоих скриптов).
- Формат отчётов и сообщений, коды выхода. Оговорено только, что «нечего
  делать» - это код 0, а любая остановка - ненулевой код.
- Как тесты получают локальный клон оригинала (переменная окружения или
  параметр), фикстуры модульных тестов.
- Мелкие случаи импорта: нет `marketplace.json` в теге, уже существует ветка
  `sync/<тег>`.
- Сравнение версий по semver - своя маленькая функция, без зависимостей.
- Точный текст README, CHANGELOG и CLAUDE.md в рамках разделов 5, 8 и 9.

## 14. Проверенные факты

### Claude Code

Источник - context7 (code.claude.com/docs), проверено 2026-11-07 и
2026-11-08. Поведение CLI проверено на CC 2.1.319, 2026-11-08.

- `name` из `plugin.json` задаёт пространство имён скиллов и агентов. Ставят
  по `name@marketplace`.
- В `marketplace.json` обязательны `name`, `owner.name` и `plugins`.
  `owner.email` и `owner.url` - необязательные. Без `description` validate
  предупреждает. Два marketplace с одним именем у пользователя быть не могут.
  Наше имя не входит в зарезервированные.
- В `plugin.json` поле `author` - это `name` плюс необязательные `email` и
  `url`. `homepage` должен разбираться как URL, иначе плагин не загрузится.
  Поле `hooks` грузится вместе с `hooks/hooks.json`.
- `source: ./plugin` работает для marketplace типов github, git, file и
  directory. Плагин копируется в `cache/<marketplace>/<plugin>/<version>/`,
  файлы вне его папки не копируются.
- Версия: сначала `version` в `plugin.json`, затем в записи marketplace. В оба
  места не ставить. Новая копия приходит, только когда версия отличается от
  установленной. Версия задаёт имя папки кэша.
- Автообновление включено по умолчанию только у marketplace Anthropic. У
  остальных его включают в `/plugin`, Marketplaces, Enable auto-update, или
  полем `autoUpdate` в `extraKnownMarketplaces`.
- После обновления папка прошлой версии помечается `.orphaned_at` и
  удаляется через 14 дней.
- `claude plugin install <плагин> --marketplace <owner/repo>` сам добавляет
  marketplace, scope по умолчанию `user`. Работает с 2.1.275.
- `claude plugin validate <путь> [--strict] [--json]`, `--json` есть с
  2.1.259. Поведение на нашей раскладке описано в 7.3.
- После сжатия контекста вызванные скиллы возвращаются первыми 5 000 токенами
  каждый, всего не больше 25 000 токенов; самые старые отбрасываются первыми.
- `--plugin-dir` на одну сессию заменяет установленный плагин только с тем же
  именем.
- Зависимости плагина ставятся, только если в корне плагина есть
  `package.json` и lock-файл. У оригинала в корне lock-файла нет.
- `skillOverrides` не действует на скиллы плагинов.
